Empact 中国的官方网站，线上地址 **https://empact.cn/**。网站内容通过图形化后台维护，更新业务介绍、案例、照片和招聘信息都不需要改代码。

## 一、网站内容介绍

### 1.1 这个网站是做什么的

empact.cn 是 Empact 中国的对外官网，用中文向访客介绍公司是谁、做什么业务、做过哪些项目，并提供咨询和应聘入口。页面打开快、手机电脑都能看；访客看到的内容来自后台最近一次发布成功的版本。

### 1.2 首页：四个板块

打开首页，从上到下依次是：

1. **品牌与照片墙**：Empact 标志的开场动画，下方是一条自动横向滚动的活动照片带（照片在后台「首页照片」里维护，见第二部分）。
2. **我们是谁**：公司简介。
3. **四大业务入口**：青少年项目、企业服务、学校业务、社区业务四张卡片。
4. **咨询入口**：引导访客填写咨询表单。

### 1.3 四大业务与 17 个细分业务

| 业务大类 | 地址 | 细分业务 |
| --- | --- | --- |
| 青少年项目 | `/youth/` | 国际人才培养模型、公益社创体验、演讲类表达、AI学习力课程、SEL社会情感学习、学员故事与家长说 |
| 企业服务 | `/corporate/` | 企业志愿者、CSR与公益咨询；AI×组织变革与智能赋能；领导力激发与体验创新；职场心理韧性培养与压力释放；商学院管理创新学科课程；公益品牌出海 |
| 学校业务 | `/school/` | 教练型智慧父母&青少年成长导师、AI×社会创新×PBL课程、演讲比赛及演讲辅导 |
| 社区业务 | `/community/` | 社区志愿者机会、朝夕有爱社区公益 |

- 每个细分业务有自己的介绍页；页面下方列出该业务**已发布**的项目案例卡片，暂时没有案例的业务会显示「项目计划中」。
- 「国际人才培养模型」是固定的方法论介绍页，不挂载案例卡片，新增案例时也不能选它作为所属业务。
- 点案例卡片有两种情况：跳转到微信公众号等外部文章（外链案例），或打开站内图文详情页。
- 社区业务下还有一张 **ChatCircle** 卡片，点击跳转到独立平台 chatcircle.empact.cn（那是另一套系统，不由本网站后台维护）。
- 青少年项目下的「国际人才培养模型」页面（`/youth/international-talent-model/`）介绍 Empact 的人才培养方法论。

### 1.4 其他页面

| 页面 | 地址 | 说明 |
| --- | --- | --- |
| 关于 Empact | `/about/` | 公司介绍、奖项等 |
| 加入我们 | `/join-us/` | 团队介绍、办公空间照片、在招岗位 |
| 招聘申请 | `/join-us/apply/` | 应聘者填写的申请表 |
| 咨询 | `/contact/` | 访客咨询表单，提交后以邮件发送给公司 |
| 隐私政策 / 使用条款 | `/privacy/`、`/terms/` | 法律声明页面 |

页脚底部有「后台管理」链接，是工作人员登录后台的入口（见第二部分）。

### 1.5 内容是怎么更新的（重要概念）

网站内容不是直接改网页文件，而是：

1. 工作人员在**后台**编辑内容，保存为**草稿**；
2. 确认无误后点**发布**，系统用最新内容生成官网的一个完整新版本并切换上去；
3. 访客始终看到最近一次发布成功的版本——后台里没发布的改动，访客看不到。

因此改错了可以慢慢改，发布失败也不会影响旧网站。当前线上版本与待办记录在 [交付验收状态](docs/planning/readiness.md)；任何人都可以通过 https://empact.cn/release.json 查看线上的代码版本号和内容版本号。

## 二、后台运维教程

> 这部分面向负责更新网站内容的同事，不需要任何编程知识，按步骤操作即可。

### 2.1 先记住三条规矩

1. **保存 ≠ 发布。** 点「保存」只存了草稿，官网不会变；点「发布到官网」之后访客才能看到。
2. **一次发布只影响当前这一条内容。** 发布一个案例不会把其他草稿一起带上线。
3. **发布失败不会搞坏官网。** 失败后官网保持原样，把失败提示截图发给技术维护人即可。

### 2.2 登录后台

1. 打开 https://empact.cn/admin/（或点官网页脚的「后台管理」）。
2. 输入用户名（或邮箱）和密码。账号由技术维护人创建，忘记密码找维护人重置。
3. 登录后进入「业务与案例」工作台。

后台主要入口：

| 入口 | 用途 |
| --- | --- |
| 新增项目 | 新增一个案例 / 项目 |
| 管理已发布项目 | 查看、修改、撤下已上线的内容 |
| 管理草稿 | 继续编辑还没发布的内容 |
| 新增业务类型 | 新增业务、维护业务介绍、调整业务顺序 |
| 首页照片 | 维护首页首屏的照片带 |
| 招聘管理 | 发布、修改、关闭招聘岗位 |
| 办公空间照片 | 维护「加入我们」页的办公室照片 |

### 2.3 新增一个案例（最常用操作）

1. 进入「新增项目」，点击「新增项目」。
2. 填写**名称**、**简短介绍**，选择**所属业务类型**（如「公益社创体验」），案例会显示在该业务的页面下。点「创建并编辑」。
3. 三个选填字段，没有可靠信息就留空：
   - **活动日期**：活动发生的日期，格式如 `2026-09-23`；注意是活动日期，不是文章发布时间。
   - **活动时间说明**：多日活动或长期安排，如「9月23日至25日」「长期」「每周六」。
   - **地点**：活动发生地。
4. 设置**项目封面**：从媒体库选图或上传新图。要求 JPG / PNG / WebP 格式、单张不超过 5 MB；并填一句**替代文字**（一句话说明图片内容）。优先使用有公开使用许可、确实属于该活动的照片。
5. 详情展示方式**二选一**：
   - 已有公众号文章 → 填**详情外链**，读者点卡片会直接跳转到该链接；
   - 需要官网文章 → 外链留空，在**网页正文**里写内容、插图片。
   - 另有「来源名称」「来源链接」两个选填项，仅用于给站内文章标注出处，不影响跳转。
6. 点**保存草稿**，再点**预览草稿**，检查标题、摘要、封面、所属业务、时间地点和正文。（预览链接需要登录才能看，有效期一小时。）
7. 确认无误后点**发布到官网**，在弹窗中确认，等待上线结果。注意：该案例所属的业务类型必须先发布过。
8. 打开官网对应的业务页面，确认新卡片已出现、时间地点正确；站内文章再点开详情页检查一遍。

同样的步骤也收录在 [在官网后台新增案例](docs/planning/content/case-upload-guide.md)。

### 2.4 修改已上线的内容

进入「管理已发布项目」，找到要改的项目，编辑后保存，再点**发布更新**。只保存不发布时官网保持原样，这条内容会显示「有未发布修改」。

### 2.5 暂时下线（撤下）与删除

- **撤下**：内容从官网消失，但保留在「管理草稿」里，以后可以重新发布；也可以把项目转移到其他业务类型下。
- **删除**：撤下并删除记录。**下面还有案例的业务类型不能删除**，需先处理完它名下的案例。历史版本和历史引用过的图片会保留，用于恢复。

### 2.6 新增业务类型、调整业务顺序

1. 进入「新增业务类型」。新业务需归入四个分组之一：企业、青少年、学校、社区；也可以在这里修改已有业务的名称和介绍。
2. 页面按分组展示看板，拖动卡片手柄或用上下箭头调整组内顺序。**不能跨分组拖动**；青少年的「国际人才培养模型」固定排最前，不参与排序。
3. 排序改动自动存为草稿；逐项把显示「有未发布修改」的业务**发布**之后，官网上的顺序才会变。
4. 如果提示顺序已被其他人修改，刷新页面再重试（避免覆盖同事的修改）。

### 2.7 首页照片

1. 进入「首页照片」入口。
2. 选择展示样式：**纯照片**或**胶卷**（只是外观不同，内容一致）。
3. 添加图片、拖动排序、可选填描述，然后保存。
4. 点**生成预览**，打开预览确认效果，再点**发布预览版本**。
5. 首页照片的发布只更新首页照片，不会带上其他栏目的草稿。

### 2.8 招聘岗位与办公空间照片

**招聘岗位**（「招聘管理」入口，首次进入会提供三个示例岗位，可直接改或删）：

1. 填写岗位名称、类型、地点、简介、工作职责、任职要求和到岗安排；职责与要求每行一条。
2. **岗位 ID** 用英文小写、数字和连字符（如 `operation-intern`），发布后尽量保持稳定。
3. 确认是真实招聘信息后，**取消「示例岗位」标记**——示例岗位只出现在预览里，不上正式站，也不接收申请。
4. 保存 → **生成预览** → 打开预览检查 → **发布预览版本**。每次修改后都要重新保存和预览再发布。
5. 招聘结束：把状态改为「已关闭」或删除岗位，再预览、发布。官网和申请下拉框会同步移除，已打开旧表单的申请也会被拒绝。
6. 暂时没有真实岗位时，官网自动显示「目前暂无开放岗位」。

**办公空间照片**（「办公空间照片」入口）：添加照片行、选择或上传图片、填写必填的**图片说明**（最多 200 字），可拖动排序、替换或删除。保存后同样走「生成预览 → 发布预览版本」。删除全部照片并发布后，「一起工作的地方」区块会从官网隐藏。

### 2.9 图片与媒体库注意事项

- 只支持 JPG、PNG、WebP，单张不超过 5 MB；每张图都要填替代文字。
- **正在被草稿或已发布内容引用的图片不能删除**，防止已上线页面出现裂图。
- 换图的正确做法：上传新图 → 在内容里改用新图 → 发布；不要试图删旧图来替换。
- 只用确认有公开授权的照片；拿不准就先问，不要用别的活动照片顶替。

### 2.10 咨询表单与收件

访客在 `/contact/` 填写咨询，必填项是：咨询方向、称呼、一种联系方式、需求说明、同意隐私政策。提交成功后，系统以**邮件**形式把内容发到公司指定收件箱；招聘申请走同一个收件通道。

- 访客提交失败会看到明确提示，系统不会假装成功。
- 表单现在已开放。管理员可进入后台「收件设置」，分别修改「咨询收件邮箱」和「招聘收件邮箱」；初始均为 `enquiries@empact.asia`。保存后对后续提交生效，无需发布页面或重启服务；不会修改网站展示的公开邮箱。
- 如果访客反馈提交不了，或想确认邮件真的送达，联系技术维护人处理并做一次真实收件验证。

### 2.11 常见问题

| 情况 | 处理 |
| --- | --- |
| 忘记后台密码 | 找技术维护人用管理员命令重置 |
| 发布失败 | 官网保持旧版本，不会坏；截图发给维护人 |
| 保存时提示冲突 | 有同事同时在改这条内容，刷新页面后重做 |
| 想删掉一个业务类型 | 先把该业务下的案例撤下或转移，才能删除业务 |
| 改了内容但官网没变 | 大概率只保存了草稿，回到该内容点「发布到官网 / 发布更新」 |

技术维护人排查发布问题时，发布日志在服务器 `$RUNTIME_DIR/releases/<回执 ID>/build.log`，草稿预览日志在 `$RUNTIME_DIR/build-logs/<预览 ID>.building.log`，日志只在服务器可见。

## 三、开发指南

> 面向第一次接触本项目的开发者或 AI 助手。读完应能独立完成：跑起本地环境 → 改代码 → 通过检查 → 提 PR → 确认上线。

### 3.1 技术栈与架构

- **官网前台**：Astro 7 静态站点（`apps/site`），构建输出纯静态 HTML。
- **内容后台**：Payload CMS 3（基于 Next.js 16，`apps/cms`），SQLite 数据库，负责内容模型、鉴权、后台 UI、受保护的草稿预览和发布器。
- **内容契约**：`packages/content` 定义发布快照的 schema、发布校验和本地种子数据（含 17 个细分业务与案例目录）。
- **发布模型**：后台保存草稿 → 发布时用已批准内容重建整站静态产物 → 原子切换 `RUNTIME_DIR/current` 指向；构建失败保留旧站。代码部署不审批、不发布 CMS 草稿。
- **线上环境**：阿里云 ECS（106.15.44.81），Caddy 网关（与 ChatCircle 共用），systemd 服务 `empact-public` / `empact-cms`。架构细节见 [工程架构和发布约定](docs/planning/implementation.md)。

### 3.2 仓库结构

| 目录 | 内容 |
| --- | --- |
| `apps/site` | 官网页面模板、交互和 SEO 输出 |
| `apps/cms` | 内容模型、鉴权、后台、受保护预览、发布器和数据库迁移 |
| `packages/content` | 快照契约、发布校验与仅供本机的种子数据 |
| `scripts/` | 静态服务、SMTP 接收、产物检查等辅助脚本 |
| `tests/` | 单元 / 集成测试与 Playwright 浏览器验收 |
| `deploy/` | Caddy 配置片段、systemd 服务、备份恢复脚本、数据库增量计划 |
| `docs/planning/` | 长期维护文档，索引见 [planning 索引](docs/planning/README.md) |
| `assets/` | 原始图片与业务资料（部分仅本机保存），见 [素材目录](assets/README.md) |
| `.data/` | 本机数据库与运行数据（**Git 已忽略，不能当临时文件清理**） |

`apps/site/src/assets` 与 `packages/content/fixtures/media` 是代码引用的资源目录，不要当作原始素材归档；`artifacts/` 是 Git 忽略的临时验收产物。

### 3.3 环境准备

要求 **Node.js 22.12+（22 系列）** 和 **npm 10**。

```bash
npm ci                            # 首次克隆后安装依赖
npm run setup:local               # 生成本机 .env 与 .data（已有配置不覆盖、不回显密钥）
npm run seed:local -w @empact/cms # 首次使用后台：建库并导入种子内容（已有内容不覆盖）
```

- 初始管理员凭据保存在 `.data/local-admin.json`（权限 600），不打印密码；后台支持用户名或邮箱登录。
- 重置管理员：`ADMIN_EMAIL=... ADMIN_PASSWORD=...(至少 8 位) npm run create-admin -w @empact/cms`，可同时用 `ADMIN_USERNAME=...` 设置登录名；会清除旧会话并解除登录锁定。
- `.env`、数据库、媒体与预览产物均被 Git 排除；真实凭据只放本机私有环境，不写入代码；不能把本机草稿部署到公开预览地址。
- Codex 工作树可直接使用 `.codex/environments/environment.toml` 的 `EmpactChinaWeb` 环境，自动完成版本检查、`npm ci` 和 `setup:local`；手动 `git worktree add` 创建的工作树需自己执行上述命令。

### 3.4 启动开发预览

```bash
npm run dev        # 后台运行，固定 http://127.0.0.1:4321
npm run dev:status # 查看后台服务状态
npm run dev:logs   # 查看日志
npm run dev:stop   # 停止
```

- 官网与 `/admin` 共用 4321，首次访问后台时按需加载 CMS，无需另起后台服务。
- **端口固定 4321，禁止自动换端口**；启动前核对占用进程的所属目录、分支和提交，复用与切换规则见 [AGENTS.md](AGENTS.md) 的「统一开发预览」。
- 首次发布前前台显示设计种子内容；发布后读取 `RUNTIME_DIR/current` 对应的已发布内容。保存草稿不改变前台，页面与样式修改由 Astro 热更新。
- 正式发布演练（非常规操作）：停止开发预览后 `npm run build:cms && npm run serve:workspace`；纯结构预览可设 `PUBLIC_ROOT="$PWD/apps/site/dist"`，正式验收前必须移除该变量。验收后恢复 `npm run dev`。
- 单独启动 CMS 等更多本机命令见 [运行、发布与恢复](docs/planning/operations/operations.md)。

### 3.5 常用命令

| 命令 | 作用 |
| --- | --- |
| `npm run check` | 类型检查（根 + site + cms） |
| `npm test` | 单元 / 集成测试 |
| `npm run verify` | 完整验证：类型、测试、预览构建与产物检查、CMS 生产构建、隔离数据库上的编辑发布流程、桌面/移动端浏览器测试 |
| `npm run test:browser` | Playwright 浏览器验收（首次需 `npx playwright install chromium --only-shell`） |
| `npm run build:preview` | 构建明确不可索引的结构预览 |
| `npm run build` | 正式构建，必须提供 `SNAPSHOT_PATH` 指向已审批快照，无快照时失败是预期行为 |
| `npm run format` | Prettier 格式化 |
| `npm audit --omit=dev --audit-level=high` | 依赖安全审计 |

### 3.6 Git 工作流（必读）

本项目有严格的协作约定，全文见 [项目协作规则](AGENTS.md)。要点：

- **不在主目录直接改代码**：从最新 `origin/main` 建独立分支和 Git worktree，编辑、检查、提交都在该 worktree 内完成；不同任务不共用 worktree。
- 主目录只用于同步 `main` 和日常 `npm run dev` 预览；任务验收需临时占用 4321 时先协调，结束后恢复主目录预览。
- Commit 遵循 Conventional Commits（`feat/fix/docs/...`）；`fix` 必带回归测试，`feat` 必带基本测试。
- 推送后创建 PR（标题 = 主 commit 的 subject），**不自动合并**；经确认后用 squash 合并。合并后先确认该任务没有独有改动、数据或活跃进程依赖，再清理对应的分支和 worktree。

### 3.7 CI 与数据库变更

- CI（`.github/workflows/ci.yml`，"Website checks"）在 PR 和 main 上运行与 `verify` 同级的检查。
- 修改 CMS 配置、集合定义、生成类型、迁移或数据库依赖时，**必须在同一 PR 提交**对应的 `deploy/schema-plans/*.json` 精确增量计划，否则 CI 直接拦截。计划的生成与校验步骤见 [自动部署](docs/planning/operations/automatic-deployment.md) 的「为后续 CMS 改动提交计划」。
- 生产数据库保留 Payload `dev / -1` 历史，**禁止直接重放原生 Payload `migrate`**，只能按上述精确增量计划升级。本机空白库可用 `npm run migrate -w @empact/cms` 初始化，升级已有库先备份并核对迁移基线。

### 3.8 部署上线

1. PR 合并进 `main` 后，"Website checks" 成功会自动触发 "Deploy production"（`.github/workflows/deploy.yml`），也可手动重试（只允许 main）。
2. 部署将 CI 验证过的构建包传至 ECS，自动备份、在副本上试跑迁移（如有）、原子切换代码指针、重启服务并做公网验收。
3. **合并 ≠ 上线。** 每次交付必须核对四项：main CI 成功 → Deploy production 成功 → 公网 [release.json](https://empact.cn/release.json) 的 `codeRevision` 等于目标提交 → 本次受影响页面实际表现正确。未核对完只能报告「已合并 / 部署中」。
4. 服务器诊断、备份恢复、发布锁处理等见 [运行、发布与恢复](docs/planning/operations/operations.md) 和 [自动部署](docs/planning/operations/automatic-deployment.md)。
